## Feature Overview

CrossPay is engineered as a non-custodial, server-driven cross-border payments engine. F3.5 adds real-time trade tracking visibility while maintaining the non-custodial architecture core to the product philosophy.
## Core Mechanics

### 1. Status Monitoring Pipeline

Trade flows through these server-determined stages:

| Stage | Code | Description | User-Visible Label |
|-------|------|-------------|-------------------|
| Pending Deposit | `pending_deposit` | Awaiting mobile money deposit or bank initiation | "Waiting for payment" |
| Escrowed | `escrowed` | Funds in trust account, awaiting verification | "Verifying payment" |
| Matching | `matching` | P2P order matching in progress | "Finding payout route" |
| Matched | `matched` | P2P order matched, funds releasing | "Almost there" |
| Disbursing | `disbursing` | Funds en route to recipient | "Paying out" |
| Completed | `completed` | Payment delivered successfully | "Done" |
| Expired | `expired` | Quote expired, money returned | "Rate expired" |
| Refunded | `refunded` | Payment returned to sender | "Refunded" |
| Failed | `failed` | Payment could not be completed | "Failed" |
| Cancelled | `cancelled` | User or system cancelled | "Cancelled" |

**Server Responsibility**: All status transitions originate from `GET /trades/{id}` endpoint.

### 2. Visual Progress Bar/Timeline

Component shows:
- Colored progress bar moving through stages
- Plain-language description at each stage
- Elapsed time at current stage
- Estimated total time (server-supplied)

### 3. Verification Hash/Receipt

- Server provides `verificationHash` or `receiptId` in trade response
- Displayed prominently in UI for user reference
- Included when contacting support or querying status
- Never a security sensitive value; reference-only

### 4. Contact Support Trigger

- Plain-language button: "Contact Support"
- Pre-fills trade reference: "Trade #t12345"
- Opens support interface with:
  - Trade ID auto-filled
  - Current status included
  - Verification hash included
  - User can add optional description
- **Never** logs PII, account numbers, or names in support request metadata

### 5. Manual Payment Claim

- User can claim "I've already paid" if payment arrived but system hasn't detected it
- Server verifies claim against actual deposit
- If valid: moves trade to `paid` status
- If invalid: shows appropriate error message
- One claim attempt per trade (idempotent)

### 6. Timeout / Countdown Handling

- Backend controls `pushTimeoutSeconds` per corridor health
- App displays countdown timer during pending stages
- When timer expires:
  - Quote may expire → offer new rate (per F3.2 behavior)
  - Deposit may be late → backend business rules apply
  - Never silently fail or absorb FX loss

**Core Principle**: No wallet, no stored balance. Escrow deposits flow to licensed partner bank/PSP omnibus trust accounts. The app only displays state; it never holds customer funds.
## API Requirements (Backend Must Honor)

```
GET /trades/{id}
- Returns: Trade status, stage, verificationHash, timeoutSeconds, nameMatch, safeguardCode
- Error shape: { error: { code, message } }

POST /trades/{id}/payment-claim
- Parameters: idempotencyKey
- Returns: Trade updated status
- Idempotent: repeated key returns original result

POST /trades/{id}/cancel
- Parameters: idempotencyKey
- Returns: Trade cancelled status
- Idempotent: repeated key returns original result
```

## Design Tensions & Resolutions

### Tension 1: Non-Custodial Model vs F3.5 Escrow

**Risk**: If CrossPay holds customer funds during P2P matching without proper licensing, central banks (CBK, BOT, etc.) will classify it as illegal deposit-taking.

**Resolution**:
- Server strictly routes escrow deposits to licensed partner bank's omnibus trust account or regulated PSP escrow account
- App correctly restricts showing safeguard claims only when server confirms `safeguardCode`
- App never displays "CrossPay holding your money" - always "Partner bank holding funds in trust"
- Legal sign-off required before F3.5 launch

### Tension 2: Match-Only Name Check vs Unverifiable Bank Destinations

**Risk**: Paying into unverifiable bank accounts carries high fraud risk in B2B or peer transfers.

**Resolution**:
- Backend returns `nameMatch: "match" | "mismatch" | "unavailable"`
- If "unavailable": show explicit warning: "This bank account name cannot be verified automatically; proceed at your own risk"
- If "mismatch": show name mismatch screen with option to correct or contact recipient
- If "match": proceed normally
- Legal counsel must approve warning wording

### Tension 3: Mobile Money Network Delays vs Polling Experience

**Risk**: Aggregator latency during USSD/STK push prompts causes timeouts before user enters PIN.

**Resolution**:
- Backend controls `pushTimeoutSeconds` dynamically based on live corridor health
- Example: 60 seconds during peak hours, 30 seconds off-peak
- App shows countdown timer during pending stages
- Manual fallback (Paybill/Till/Pay-in number) acts as safety valve
- User can always switch to manual fallback

### Tension 4: Rate-Lock Countdown vs Mobile Money Timeout

**Risk**: Quote expires while money in transit, causing silent failure or FX loss.

**Resolution**:
- Backend handles "late-arriving deposits" gracefully per business rules
- Options:
  - **Auto-execute at updated spot rate** (if deposit arrives within T hours of expiry)
  - **Place trade in `pending_user_decision` state` with "Get new rate" CTA
  - **Automatic refund` to sender if beyond grace period
- App never shows "silent failure" - always plain-language status

## Phase 2: Provider Layer - COMPLETED

Enhanced `lib/providers/trade_provider.dart` with F3.5 methods:

1. `Future<void> loadTrade(String tradeId)` - Fetches trade by ID and sets `activeTrade` state with `TradeFlowStatus.active`. Uses the repository's `getTrade` method.

2. `Future<void> claimManualPayment({required String idempotencyKey})` - Claims manual payment for the active trade using the repository's `claimPayment` method with idempotency key. Triggers a state refresh after claiming.

3. `void resetTradeTracking()` - Resets the trade tracking state to initial values (idle flow status, no active trade).

All methods integrate with the existing `TradeState` and `TradeNotifier` framework, maintaining consistency with the codebase's Riverpod patterns. The `tradeUpdated` method (already existing) is used for live server pushes.
