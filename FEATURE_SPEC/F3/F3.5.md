## Overview

CrossPay is a non-custodial, server-driven cross-border payments engine. F3.5
adds visibility into a trade after authorization: the server decides every
status change, and the app only displays what it is told. The app never holds
customer funds or a stored balance.

## Current State

Built and tested:

- `/tracker` is scrollable, with Contact support / Share invoice pinned at the
  bottom. A terminal trade pins Done alone.
- Six-stage progress bar with dictionary-backed labels, sized to fit a 360dp
  phone without horizontal overflow.
- Trade timeline card fed by `GET /trades/{id}/history`, with honest loading,
  empty and "not connected" states. It never invents events.
- Verification hash display with copy action when the server supplies a hash.
- `/support` screen with trade reference/status/hash, copy actions, an optional
  message and server-driven contact channels.
- Manual payment claim path (`POST /trades/{id}/payment-claim`) with an
  idempotency key.
- Widget/unit coverage for the tracker, support screen, timeline, config parsing,
  settings navigation and repository behavior.

Server-dependent or deliberately not built:

- Real support channel values under `/config.support` and in-app ticket/message
  submission.
- Elapsed-time and estimated-completion displays. These need server-supplied
  figures and are not shown today.
- Status timeline presentation is functional but still being refined; the
  product owner flagged it on 2026-11-10 as a follow-up.
- Live push updates. `TradeNotifier.tradeUpdated` exists; the transport is
  backend work.

## Core Mechanics

### 1. Status Pipeline

Trade flows through these server-determined stages:

| Stage | Code | Description | User-visible label |
|-------|------|-------------|--------------------|
| Pending deposit | `pending_deposit` | Awaiting mobile money deposit or bank initiation | "Waiting for payment" |
| Escrowed | `escrowed` | Funds in trust account, awaiting verification | "Verifying payment" |
| Matching | `matching` | P2P order matching in progress | "Finding payout route" |
| Matched | `matched` | P2P order matched, funds releasing | "Almost there" |
| Disbursing | `disbursing` | Funds en route to recipient | "Paying out" |
| Completed | `completed` | Payment delivered successfully | "Done" |
| Expired | `expired` | Quote expired, money returned | "Rate expired" |
| Refunded | `refunded` | Payment returned to sender | "Refunded" |
| Failed | `failed` | Payment could not be completed | "Failed" |
| Cancelled | `cancelled` | User or system cancelled | "Cancelled" |

**Server responsibility**: the server is the only source of status. The app
learns it from `GET /trades/{id}` and never advances a status locally.

### 2. Progress Bar and Timeline

The progress bar covers the six live stages from `pending_deposit` to
`completed`. Terminal outcomes (`expired`, `refunded`, `failed`, `cancelled`)
are shown as the trade's headline status when the server returns them.

The timeline is a separate card. It lists server events with their localized
status and timestamp. Until `GET /trades/{id}/history` exists, the card says the
timeline is not connected instead of fabricating steps.

Elapsed time at the current stage and estimated total time are target
behaviors only. They must come from the server and are not displayed yet.

### 3. Verification Hash / Receipt

- The server may provide `verificationHash` on the trade.
- It is displayed prominently when present and can be copied with the built-in
  clipboard.
- It is reference data, not a security credential.
- It is included in support details only when the server supplied it.

### 4. Contact Support

- Plain-language "Contact support" button, pinned at the bottom of the tracker.
- Carries the trade reference, current status and verification hash into
  `/support`. The typed `SupportTradeContext` is the normal path; legacy map
  arguments still parse.
- Users can add an optional description and copy the trade or request details.
- Contact channels (email, phone, WhatsApp, hours) come from the optional
  `support` block of `GET /config`. No channel is shown unless the server
  supplies it.
- The screen has honest loading and empty states. In-app message submission is
  not connected, so there is no fake send action.
- Also reachable from Settings -> Help & support, with no trade attached.
- **Never** logs PII, account numbers, beneficiary names or other personal data
  in support request metadata.

### 5. Manual Payment Claim

- A person can claim "I've already paid" if the payment arrived but the system
  has not detected it.
- The server verifies the claim against the actual deposit.
- Valid claim: the server moves the trade forward.
- Invalid claim: the app shows the server's error message.
- One idempotency key per claim attempt; repeating it must return the original
  result.

### 6. Timeout / Countdown Handling

Target behavior, backend-dependent:

- The backend controls `pushTimeoutSeconds` in the collection details returned
  when a trade is initiated. The payment prompt counts down from that value; the
  tracker shows no countdown.
- On expiry, the backend business rules decide whether to offer a new rate,
  wait for a late deposit, or refund.
- The app never silently fails or absorbs FX loss; it always shows a
  plain-language server status.

**Core principle**: no wallet, no stored balance. Escrow deposits flow to
licensed partner bank/PSP omnibus trust accounts. The app only displays state;
it never holds customer funds.

## API Requirements (Backend Must Honor)

```
GET /trades/{id}
- Returns: the trade object documented in `docs/api_contract.md` (status,
  amounts, optional verificationHash)
- Error shape: { error: { code, message } }

GET /trades/{id}/history
- Returns: { "events": [ { "status": "<status code>", "at": "<ISO-8601 UTC>",
  "noteCode": "<optional code>" } ] }, oldest first
- `noteCode` is optional and not displayed yet; an unknown value is ignored and
  the status label is still shown

POST /trades/{id}/payment-claim
- Idempotency: `X-Idempotency-Key` header (one key per claim attempt)
- Response body is not used; the payment step keeps polling GET /trades/{id}
- Idempotent: a repeated key returns the original result

POST /trades/{id}/cancel
- Body: idempotencyKey
- Returns: cancelled trade
- Idempotent: a repeated key returns the original result
```

`GET /config` may include the optional support block documented in
`docs/api_contract.md`.

## Design Tensions & Resolutions

### Tension 1: Non-custodial model vs F3.5 escrow

**Risk**: holding customer funds during P2P matching without the right license
would be classified as illegal deposit-taking.

**Resolution**:

- The server routes escrow deposits to a licensed partner bank's omnibus trust
  account or a regulated PSP escrow account.
- The app shows safeguard claims only when the server confirms `safeguardCode`.
- The app never says "CrossPay is holding your money"; it says the partner bank
  holds funds in trust.
- Legal sign-off is required before F3.5 launch.

### Tension 2: Match-only name check vs unverifiable bank destinations

**Risk**: paying into unverifiable bank accounts carries fraud risk.

**Resolution**:

- Backend returns `nameMatch: "match" | "mismatch" | "unavailable"`.
- `unavailable`: show the explicit "cannot be verified automatically" warning.
- `mismatch`: show the name mismatch screen with correction or recipient
  contact options.
- `match`: proceed normally.
- Legal counsel must approve the warning wording.

### Tension 3: Mobile money network delays vs polling

**Risk**: aggregator latency during USSD/STK prompts causes timeouts before the
user enters their PIN.

**Resolution**:

- Backend controls `pushTimeoutSeconds` from live corridor health.
- The app shows a countdown once the server supplies it.
- Manual fallback (Paybill/Till/pay-in number) remains available.

### Tension 4: Rate-lock countdown vs mobile money timeout

**Risk**: the quote expires while money is in transit, causing silent failure or
FX loss.

**Resolution**:

- Backend handles late-arriving deposits per business rules.
- Options: execute at the updated spot rate within a grace window, place the
  trade in a `pending_user_decision` state with a "Get new rate" action, or
  refund beyond the grace period.
- The app never shows a silent failure; it always shows a plain-language status.
