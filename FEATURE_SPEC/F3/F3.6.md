## Feature Overview

F3.6 extends the existing P2P trade flow (F3.5) with invoice generation and sharing capabilities. When a trade is initiated, the system generates a shareable invoice with QR code for P2P payment collection. This creates a seamless connection between F3.5 trade processing and P2P payment workflows while maintaining the non-custodial architecture.

## Core Mechanics

### 1. Invoice Generation

Trade flows through these invoice-related stages:

| Stage | Trigger | Output | User-Visible Label |
|-------|---------|--------|-------------------|
| Invoice Created | Trade initiation | QR code with trade reference | "Invoice Ready" |
| Invoice Shared | User taps share button | Native share sheet with QR code | "Share Invoice" |
| Invoice Claimed | Recipient scans QR code | Payment claim via payment-claim API | "Payment Claimed" |
| Invoice Completed | Trade status updates to completed | Trade confirmed | "Done" |
| Invoice Expired | ValidUntil timestamp passed | Trade moves to expired state | "Expired" |

**Server Responsibility**: All invoice status transitions originate from `GET /trades/{id}/invoice` endpoint.

### 2. QR Code Mechanics

- **Format**: QR code containing trade reference and payment details
- **Encoding**: URL-encoded deep link to trade dashboard
- **Security**: Contains truncated, safe payment reference only
- **Display**: Embedded in trade tracking interface
- **Scan Behavior**: Opens trade status page via deep link

### 3. Share Sheet Mechanics

- **Distribution**: Built-in iOS/Android share functionality
- **Content**: QR code image with trade reference
- **Accessibility**: One-tap access to trade status page
- **Analytics**: Tracking of share performance and user engagement
- **Native Integration**: iOS share extension, Android share intent

### 4. Manual Payment Claim Integration

- User can claim payment via QR code scan or manual entry
- Server verifies claim against actual deposit
- If valid: moves trade to `paid` status
- If invalid: shows appropriate error message
- One claim attempt per trade (idempotent)

### 5. Timeout / Expiry Handling

- Backend controls `validUntil` timestamp per invoice
- App displays countdown timer during pending stages
- When timer expires:
  - Trade moves to `expired` state
  - Offer new rate via F3.2 behavior
  - Never silently fail or absorb FX loss

**Core Principle**: No wallet, no stored balance. Invoice generation follows the same non-custodial architecture as F3.5. Escrow deposits flow to licensed partner bank/PSP omnibus trust accounts. The app only displays state; it never holds customer funds.

## API Requirements (Backend Must Honor)

### Existing Endpoints Enhanced

```
GET /trades/{id}
- Returns: Trade status, stage, invoice URL, verificationHash
- Error shape: { error: { code, message } }

POST /trades/{id}/payment-claim
- Parameters: idempotencyKey
- Returns: Trade updated status
- Idempotent: repeated key returns original result

POST /trades/{id}/cancel
- Parameters: idempotencyKey
- Returns: Trade cancelled status
- Idempotent: repeated key returns original result
```

### New Endpoints

```
GET /trades/{id}/invoice
- Returns: QR code URL, share URL, validUntil, amount, currency
- Error shape: { error: { code, message } }

POST /trades/{id}/share
- Parameters: idempotencyKey
- Returns: Shareable invoice link and metadata
- Idempotent: repeated key returns original result
```

## Design Tensions & Resolutions

### Tension 1: Invoice vs Trade Tracking

**Risk**: Duplicate tracking between invoice and trade status could cause inconsistencies.

**Resolution**:
- Both share same trade reference ID for unified tracking
- Invoice status derived from trade status via `GET /trades/{id}`
- Single source of truth: server-provided trade status
- Invoice displayed as read-only view of trade state

### Tension 2: QR vs Manual Payment Claim

**Risk**: Two different paths to claim payment could lead to double-collection.

**Resolution**:
- Both QR scan and manual entry trigger same `POST /trades/{id}/payment-claim` endpoint
- Idempotency key enforced per server contract
- Second claim attempt returns original result (never charges twice)
- Server validates claim against actual deposit before processing

### Tension 3: Sharing vs Security

**Risk**: Sharing QR codes could expose payment details to unauthorized parties.

**Resolution**:
- QR contains truncated, safe payment reference only
- No sensitive account or personal data in QR code
- Trade reference maps to server-validated payment
- Access controlled via server-side trade status checks

### Tension 4: Immediate vs Delayed Payment

**Risk**: Invoice available instantly but payment processed later could cause UX confusion.

**Resolution**:
- Invoice status reflects actual trade state from server
- UI shows pending/claimed/expired states clearly
- No silent failures - always plain-language status
- User notified when payment status changes

## Phase 2: Provider Layer - COMPLETED

Enhanced `lib/providers/trade_provider.dart` with F3.6 methods:

1. `Future<void> shareInvoice(String tradeId)` - Triggers invoice generation and share preparation. Uses repository's `shareTrade` method.

2. `Future<void> claimManualPayment(String idempotencyKey)` - Claims manual payment for the active trade using the repository's `claimPayment` method with idempotency key. Triggers a state refresh after claiming.

3. `Future<void> loadTrade(String tradeId)` - Fetches trade by ID and sets `activeTrade` state with `TradeFlowStatus.active`. Uses the repository's `getTrade` method.

All methods integrate with the existing `TradeState` and `TradeNotifier` framework, maintaining consistency with the codebase's Riverpod patterns.

## Phase 1: Repository Layer - COMPLETED

Added to `lib/repositories/trade_repository.dart`:

1. `Future<void> shareTrade(String tradeId, {required String idempotencyKey})` - Generates invoice and prepares share data using `POST /trades/{id}/share`

2. `Future<Invoice> getInvoice(String tradeId)` - Returns QR code URL, share URL, and metadata using `GET /trades/{id}/invoice`

3. `Future<void> claimPayment(String tradeId, {required String idempotencyKey})` - Claims manual payment using `POST /trades/{id}/payment-claim` with idempotency key

All methods use existing API endpoints from `api_endpoints.dart` and follow the established patterns in the repository. Idempotency keys are enforced per server contract.
