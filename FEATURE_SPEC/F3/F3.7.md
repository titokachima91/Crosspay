## Design Tensions & Resolutions

### Tension 1: Security vs. Convenience

**Risk**: Strong security (PIN, biometric) creates friction for frequent users.

**Resolution**:
- Configurable timeout for PIN re-entry
- Biometric as primary, PIN as fallback
- Stay signed in option with refresh tokens
- Server-controlled security policies

### Tension 2: Multi-Language vs. App Size

**Risk**: Additional language files increase app size significantly.

**Resolution**:
- Dynamic language download from server
- Cache language files locally
- Only download languages user selects
- Server provides language availability

### Tension 3: Analytics vs. Privacy

**Risk**: Transaction analytics could expose sensitive user data.

**Resolution**:
- Analytics data anonymized before transmission
- User opt-in for analytics sharing
- No PII in analytics payloads
- Server-side aggregation only

### Tension 4: Real-Time vs. Battery Life

**Risk**: Continuous route health monitoring drains battery.

**Resolution**:
- Server-controlled polling intervals
- Background fetch only when app is active
- Cache corridor health locally
- User-configurable refresh frequency

## Feature Scope

### 7.1 Advanced Payment Routing

**Objective**: Enable intelligent route selection with multiple corridor options and real-time fee comparison.

**Key Components:**
- Multi-corridor route comparison UI
- Real-time fee and exchange rate display
- Route preference settings (fastest, cheapest, most reliable)
- Corridor health monitoring integration
- Fallback route selection when primary corridor is unavailable

**API Requirements:**
- `GET /trade/routes` - Returns available routes with fees and timing
- `GET /trade/corridor-health` - Returns corridor status and health metrics
- `POST /trade/select-route` - User route selection with idempotency key

**Acceptance Criteria:**
- [ ] User can view multiple route options with fees and timing
- [ ] Route selection persists across sessions
- [ ] Fallback route offered when primary is unavailable
- [ ] Route health status displayed (healthy, degraded, unavailable)
- [ ] All route data comes from server (no hardcoded values)

### 7.2 Multi-Language Support Expansion

**Objective**: Expand localization beyond en/sw to support additional languages for target markets.

**Key Components:**
- Additional language files (fr, ar, pt, etc.)
- Language detection based on device locale
- Right-to-left (RTL) layout support for Arabic/Hebrew
- Localized error messages and status labels
- Currency formatting per locale

**API Requirements:**
- `GET /config/languages` - Returns supported languages
- `GET /localization/{lang}` - Returns translation strings

**Acceptance Criteria:**
- [ ] At least 3 additional languages supported
- [ ] RTL layout for Arabic/Hebrew
- [ ] All UI text localized (not hardcoded)
- [ ] Language preference persisted
- [ ] Server provides available language list

### 7.3 Enhanced Security Features

**Objective**: Add PIN/biometric lock, session management, and security enhancements.

**Key Components:**
- PIN setup and verification flow
- Biometric authentication (fingerprint, face ID)
- Stay signed in with refresh token rotation
- Session timeout configuration
- Security settings screen

**API Requirements:**
- `POST /auth/refresh` - Token refresh
- `POST /auth/logout` - Session termination
- `GET /auth/security-settings` - Returns security configuration

**Acceptance Criteria:**
- [ ] PIN required on app launch after timeout
- [ ] Biometric fallback to PIN
- [ ] Refresh token rotation on each use
- [ ] Session timeout configurable by server
- [ ] No sensitive data stored locally
